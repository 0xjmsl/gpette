gpette manual

A chat bot server for XMTP. People message your bot from any XMTP app; gpette hands each message to a language model and sends the answer back. This page is for the person running the bot and for an AI assistant helping them set it up.

1. The two pieces

A gpette bot is two programs on the same machine, talking plain HTTP:

  • xmtp_daemon holds the bot's XMTP identity (its key) and talks to the network. It knows nothing about models.
  • gpette holds the rules, the conversations and the model calls. It never holds the XMTP key.

Why two pieces, and why these languages

  • The key lives apart from the AI. The model can run tools; it should never be one tool call away from the bot's identity. The daemon keeps the key, gpette never sees it.
  • One key, several machines. Because the key sits in its own small program, you can run it twice (two installations of the same bot) and give each its own gpette (§11).
  • Rust daemon: XMTP's core library (libxmtp) is Rust. Using it directly hands over each message's raw content, so custom content types (captions, galleries, files) arrive intact. XMTP's ready-made Node SDK decodes standard types itself and drops parameters custom codecs rely on.
  • Python gpette: every model provider ships an official Python SDK, a new tool is one .py file, and Claude Code is called as a CLI. That is where the bot changes most, so it stays the easy part to edit.
  • Plain HTTP between them: any language can stand in for either side. Write your own bot behind the daemon's webhook if you like.

2. Run it

Python 3.11+ for gpette; the daemon is one binary. Two commands, two terminals:

# 1. gpette (reads gpette.toml next to main.py)
pip install -r requirements.txt
cp gpette.example.toml gpette.toml        # edit it
python main.py

# 2. the daemon, pointed at gpette's port
XMTP_WEBHOOK_URL=http://127.0.0.1:4849 ./xmtp_daemon

The daemon creates the bot's key on its first run (secrets/bot.key, plus secrets/db.key for its database). Back both up. Lose the key and you lose the bot's address. Its log prints the address: DM it from any XMTP app.

GPETTE_CONFIG=/path/other.toml python main.py runs gpette with another config file.

Windows (PowerShell): copy gpette.example.toml gpette.toml, then $env:XMTP_WEBHOOK_URL="http://127.0.0.1:4849"; .\xmtp_daemon.exe and $env:GPETTE_CONFIG="other.toml"; python main.py.

Two bots on one machine = two pairs. Simplest: one folder per bot, each with its own copy of both. Or give each daemon its own key, database and port (XMTP_KEY_FILE, XMTP_DB_KEY_FILE, XMTP_DB_DIR, XMTP_HTTP_ADDR), and each gpette its own config with its own [server] port, data_dir and [daemon] url.

3. What happens to a message

  1. Filter: answer/ignore rules. Used when another gpette shares this bot's identity, or to mute someone (§6).
  2. Profile: which environment handles it: model, folder, tools, prompt, gate. A group chat is matched by its id, then by the sender (§7).
  3. Gate: open, password, none, or your plug-in. Plus an optional daily cap per person (§6).
  4. Store + queue: the message is saved, then put on one queue with one worker. Messages are handled one at a time, in order, across all chats.
  5. Chat controller: loads the recent history, optionally compacts it, adds sender names (groups) and the prompt.
  6. Model: the profile's provider. Claude Code resumes the chat's session in its folder. API models get the history and the tool list.
  7. Tool loop (API models only): a tool call runs a Python tool and its result goes back to the model, up to 50 rounds.
  8. Reply: stored, then sent through the daemon.

Compaction ([compaction], on by default): each chat keeps one running summary. A reset clears it; provider = "disabled" turns it off.

API models: when more than after messages (30) follow the summary, all but the latest keep (10) are folded into it in one call, made by the chat's own model (provider = "same") or by the one you name. The model sees the summary plus the recent messages word for word, so a long chat costs one extra call every 20 or so messages.

Claude Code ([compaction.claude_code]): the trigger is the size of the session, read after each run. From topic_tokens (300,000) on, one short call checks each new message, and a new subject cuts. From force_tokens (400,000) on, the next message cuts. A cut folds gpette's log of the chat into the summary (up to summary_words, 1,000) and drops the session; the next one starts with the summary and the latest keep messages. With provider = "same" both calls are one-shot claude runs on model (Sonnet), with no session and no tools. A failed summary call cuts nothing. /compact cuts at any size.

Everything is in gpette.toml. API keys never go in it: they come from the environment. Paths are relative to the file.

6. Who gets answered

Two stages, both silent when they say no:

Filter: does this gpette handle it?

[filter]
default = "answer"                 # when no rule matches: answer | ignore
[[filter.rules]]                   # checked in order, first match wins
name = "muted"
action = "ignore"
inboxes = ["<inbox id>"]           # DM senders
# accounts = ["0x..."]             # needs an owner_resolver (§13)
# groups = ["<group id>"]          # group chats, by id only

Gate: may this person talk?

[gate] kindBehaviour
openEveryone is answered (default).
passwordA stranger's first DM must be exactly password. They get welcome and are in for good. At most new_people_per_day new people a day. Anything else from a stranger is dropped. A group is answered when one of its members is in. The password never works inside a group.
noneNo one. Useful on a profile served by another machine.
my_package.my_gateYour own rule, e.g. an allowlist, a membership check, a chain lookup (§13).

A profile can pick its own gate (gate = "open"). messages_per_person_per_day (> 0) caps any gate. The password is one, global; there is no per-profile password.

Hard-coded people: list their inbox ids in a profile with gate = "open" and make the top-level gate password or none. They are always answered; everyone else meets the gate.

7. Profiles and sessions

[profiles.friends]
members = ["<inbox id>", "<group id>"]   # who this applies to
provider = "gemini"
system_prompt = "You are a friendly helper for a small group of friends. Be brief."
tools = ["setTimer", "listTimers"]       # Python tools it may call

Matching: a group message by the group id first, then by the sender. Unmatched DMs use the top-level settings. Unmatched groups depend on [claude_code] groups:

  • "sandbox" (default): each group gets its own empty folder under group_workdir and no tools. Safe for groups you don't control.
  • "default": every group gets the top-level folder and tools (e.g. the knowledge folder), still one memory per group.

To give one group something special, list its id in a profile.

Keys: members, provider, model, workdir, allowed_tools, system_prompt, system_prompt_file, sessions, gate, tools, max_turns, timeout_secs, privacy, inherit_user_settings, transcripts. All optional.

sessions / [sessions] routingMemory works like
per_conversationOne memory per chat (default).
sharedEvery DM of the profile continues one memory.
per_accountOne memory per person, across their inboxes and chats. "Person" comes from owner_resolver; without one, each inbox is a person. Groups stay per group.

Anyone can send /reset (or "reset conversation") to start over.

8. Claude Code bots

  • Folder (workdir): the bot runs there. Its CLAUDE.md is the personality and rules. Put the knowledge the bot should read in the same folder.
  • Tools (allowed_tools): only the listed tools exist. ["Read","Glob","Grep"] = read and search the folder. [] = talk only. ["Read(./images/**)"] = see pictures people send, nothing else (incoming pictures are saved in <workdir>/images/). ["*"] = every tool, governed by the folder's settings (owner bots only).
  • Never keep secrets in a bot's folder: a bot that may read there can be asked to read anything there.
  • privacy = true (default): the bot never reveals paths, user names, machine or config details.
  • transcripts = true: each person's chat is written to conversations/<person>/ so a read-only bot can look up old conversations; each person's bot is blocked from the others' folders.
  • inherit_user_settings (default false): true loads the host user's own Claude settings and memory. Only for a bot that answers its owner.
  • Limits: max_turns, timeout_secs; talk-only runs give up after fenced_timeout_secs.

9. Timers and tools

Tools (API providers): every tools/name.py holding a function name is a tool. The docstring is what the model sees; a Parameters: section describes the arguments; a _conversation_id argument is filled by gpette. Files starting with _ or sys_ are skipped. A profile's tools list limits them.

Timers ship as tools: setTimer, listTimers, editTimer, cancelTimer. The model sets one ("remind me at 8"); every timer_check_secs gpette queues the due ones as a message Timer fired: <instructions> in that chat. One-shot or recurring. If the model answers exactly [NO_REPLY], nothing is sent: good for quiet background jobs.

11. One bot, two machines

XMTP lets one identity run on several machines (up to 10 installations); each receives every message. Run the same key on two machines, each daemon with its own XMTP_DB_DIR, and give each gpette opposite filter rules so exactly one answers each person.

# gpette on machine A (the owner's)          # gpette on machine B (public)
[filter]                                       [filter]
default = "ignore"                             default = "answer"
[[filter.rules]]                               [[filter.rules]]
action = "answer"                              action = "ignore"
inboxes = ["<owner inbox id>"]               inboxes = ["<owner inbox id>"]

Groups are matched by group id only, so the same machine always answers a given group. In the example, B answers all groups; add groups = "default" under B's [claude_code] if groups should read B's folder too.

Several different bots on one machine: one daemon + one gpette per bot, each pair on its own ports, key and data folder.

12. Check it

  • Admin panel: http://127.0.0.1:4849/admin (this machine only). Each chat's last route: filter rule, profile, gate decision, session. A "who would handle this?" box answers without sending. JSON: /api/admin/routes, /api/admin/setup, /api/admin/explain?sender=…&conversation=…&kind=dm|group.
  • Log: data/logs/app.log. Look for Filter: ignored, gate refusals, run summary (turns, cost, denied tools), xmtp_http_bridge: sent to.
  • Test without XMTP: python tests/harness.py tests/scenarios/security.toml starts a fake daemon and your config, sends scripted messages and checks the replies. Copy a scenario to test your own setup.
  • Move history: python scripts/history.py export file.jsonl / import.

13. Plug-ins

A plug-in is a Python module on PYTHONPATH, named in the config by its dotted path. It reads its settings with from config import plugin_settings; plugin_settings("name") from [plugins.name].

KindConfigThe module provides
Gate[gate] kind = "pkg.mod"class Gate with check_message(message, kind=None) → {"action": "allow"} or {"action": "reject"}
Who a person is[sessions] owner_resolverowner_for(inbox_id) → a stable id (e.g. an account) or None
Sender names[senders] resolverresolve(inbox_id, address=None) → a name or None
Storage[storage] backendclass ConversationDB with the SQLite one's methods
# mygate.py: answer only listed inboxes
from config import plugin_settings
class Gate:
    def __init__(self, db=None):
        self.ok = set(plugin_settings("mygate").get("allow", []))
    def check_message(self, message, kind=None):
        return {"action": "allow" if message.get("senderInboxId") in self.ok else "reject"}

# gpette.toml
[gate]
kind = "mygate"
[plugins.mygate]
allow = ["<inbox id>"]

What a gate receives. message is a dict: senderInboxId, conversationId, kind ("dm" / "group"), content = {"type": "text", "value": "…"}. Besides allow / reject it may return {"action": "auth_success", "response": reply}: gpette sends reply (a message dict) and stops there. That is how the built-in password gate says welcome.

# twopass.py: two passwords, two circles of people (one gpette)
import json, os, time
from config import plugin_settings
class Gate:
    def __init__(self, db=None):
        s = plugin_settings("twopass")
        self.words = s.get("passwords", {})          # {"pancake": "family", "taco": "friends"}
        self.file = s.get("file", "./data/twopass.json")
        self.who = json.load(open(self.file)) if os.path.exists(self.file) else {}
    def check_message(self, message, kind=None):
        who, conv = message.get("senderInboxId"), message.get("conversationId")
        c = message.get("content") or {}
        text = (c.get("value") if isinstance(c, dict) else c or "").strip()
        if text in self.words:
            self.who[who] = self.words[text]
            json.dump(self.who, open(self.file, "w"))
            return {"action": "auth_success", "response": {"role": "assistant",
                "content": {"type": "text", "value": "Welcome, " + self.words[text] + "."},
                "conversationId": conv, "senderInboxId": who, "timestamp": int(time.time())}}
        return {"action": "allow" if who in self.who else "reject"}

# gpette.toml
[gate]
kind = "twopass"
[plugins.twopass]
passwords = { pancake = "family", taco = "friends" }

A gate decides who gets in, not which setup answers. To give the two circles different bots, list their inboxes in two profiles once you know them (the admin panel shows each sender's inbox id).

14. Troubleshooting

SymptomCheck
No reply at allDaemon's XMTP_WEBHOOK_URL = gpette's port? app.log shows the message? The admin panel's decision column.
Message arrives, nothing sentThe gate (password strangers are dropped), the filter, the daily cap.
Reply never reaches the app[daemon] url wrong; daemon log for /send errors.
Two machines both answer, or neitherTheir filter rules overlap or leave a gap.
Bot can't see imagesClaude Code needs Read (or Read(./images/**)). A group in no profile with groups = "sandbox" has no tools, so it can't see pictures: list the group in a profile.
claude not found / signed outThe CLI must be on PATH and signed in for the user running gpette.
LM Studio error at startLM Studio must be serving before gpette starts.
Profile not usedExact inbox or group id in members; group id wins over sender.

15. For AI assistants setting this up

  1. Ask: which model(s)? Who should be answered (everyone, password, a list)? Should the bot read files? One memory per chat or per person? Groups?
  2. Start from gpette.example.toml; change only what the answers require. Keep [server] host = "127.0.0.1".
  3. API keys go in the environment, never in the file. Claude Code needs the CLI signed in, no key.
  4. For a Claude Code bot, create the workdir with a CLAUDE.md. Never put secrets in that folder.
  5. Prefer the narrowest tools: [] or ["Read","Glob","Grep"]. Use ["*"] and inherit_user_settings only for the owner's own profile. ["*"] alone makes every tool exist but lets only what the settings files approve run (a bot runs in don't-ask mode, so anything else is refused); name tools beside it to approve them outright: ["*", "Bash", "Edit", "Write"].
  6. Inbox ids are 64 hex characters (no 0x); group ids are 32 hex characters. Both appear in app.log and the admin panel once a message arrives.
  7. Verify: start both pieces, send a DM, open /admin; or write a harness scenario first.
